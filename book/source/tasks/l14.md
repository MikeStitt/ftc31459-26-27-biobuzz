# L14: give the driver a button that parks the robot

## What you will have when this is done

Press Y and the robot drives itself to one spot on the field and stays there. Touch a stick and the
driver has it back at once, from wherever the robot got to.

## Before you start

- [L11](l11.md) is finished, because the driver's half of this drives field relative.
- [L10](l10.md) is finished, so a follower holding a pose is not new.
- [task.l8](l8.md) is done, so the robot knows where it is. The target is a spot on the field, not a
  distance from the robot, and a robot with the wrong pose drives to the wrong place.
- About 3 m by 3 m of clear floor.

You write 21 lines in one file, `L14DriveToPoseOpMode.java`. The target is given: `POSES.of(120, 72,
90)`.

## The steps

### Step 1: put a command on the Y button

`bindings()` runs once, when the OpMode starts. TODO 1 ties `gamepad1.y` to an instant command that
calls `follower.hold(TARGET)` and sets `drivingItself = true`.

An **instant** command does its work and finishes in the same breath. This one sets the follower's
mode and ends, and the follower goes on holding long after the command is gone. The only thing that
takes it back out of HOLD is a call to `manual()`. So the lesson has to remember by itself that it
started something, which is what `drivingItself` is for.

Watched in the test harness: the command body runs inside `loopBefore()`, on the same loop the
button goes down, before your own driving code. So `drivingItself` is already true the first time
step 2 reads it.

### Step 2: decide who gets the wheels

TODO 2 and TODO 3 are one `if` inside another. The three sticks and `driverWantsControl` are read
for you above the blank, with a band of 0.1, so what is left is the choosing. There are three
cases and they go in this order.

- The command is running and the sticks are near zero. Publish `AUTO`, hand the wheels back with
  `drivetrain.releaseCommandedWheels()`, and `return`. The follower is holding the pose, and the
  lesson's job is to keep out of its way.
- The command is running and the driver has moved a stick. Forget the command with
  `drivingItself = false` and call `follower.manual(0, 0, 0)`, which is the one call that leaves
  HOLD. The three zeros are thrown away; the next line commands the wheels.
- Nothing is running. Publish `DRIVER` and drive field relative, exactly as L11 does.

The `return` in the first case is the whole shape of it. Leave it out and the code walks straight on
into the take-over lines, so pressing Y cancels its own command on the same loop.

**You'll know it worked when** this prints `BUILD SUCCESSFUL`:

```
./gradlew :TeamCode:testDebugUnitTest --tests '*LessonsTest.l14*'
```

**If it didn't**, open the report gradle names. Two mistakes share each message, so both are worth
reading.

- `the command is driving, not the sticks expected:<HOLD> but was:<MANUAL>`. Nothing put the
  follower in HOLD and left it there. Either TODO 1 is still open, so the button does nothing, or
  the `return` is missing and the loop cancels the hold the instant it starts.
- `manual control returns expected:<MANUAL> but was:<HOLD>`. The follower is holding and the
  driver cannot get it back. Either the outer `if` is never entered, because `drivingItself` is
  never set true, or it is entered and `follower.manual(0, 0, 0)` is not called.

Two of those are worth doing on purpose once. Take the `return` out and watch the first message
appear, then put it back and watch it go.

:::{admonition} Mistakes the test here cannot see
:class: note
Leaving `releaseCommandedWheels()` out passes. Nothing is commanded yet in the test, so there is
nothing to hand back. On the floor it is the mistake you notice most: the wheels stay at whatever
the driver last asked for, and the follower's answer never reaches them. Watched in the harness,
sliding
right and then pressing Y, the follower says HOLD for a whole second while the robot slides on from
68 in to 26 in and never turns toward the target.

Leaving out `drivingItself = false`, and swapping `fieldRelative` for `sticks`, both pass as well.
So does dropping both `drive/mode` publishes. The mode is for Panels, and a driver who says "it took
off on its own" and a graph that says which of the three cases was in force settle it between them.
:::

### Step 3: drive it and then take it back

Send the code to the robot. Run `L14 Drive To Pose` and press PLAY. Drive somewhere with the left
stick, let go, and press Y.

**You'll know it worked when** the robot drives off to the target on its own and sits there. Then
push the left stick and it is yours again, without pressing anything else.

**If it didn't**, and the robot drives somewhere that is not the target, the pose is wrong rather
than this lesson. [task.l8](l8.md) is where the pose comes from.

**If it didn't**, and it creeps up to the target and hunts back and forth, that is the follower's
tuning. `task.autotune` is where those numbers come from.

:::{admonition} What has not been done here
:class: note
Step 3 has not been performed on a robot for this page. Every message and number above was measured
in the test harness, where the robot covers the 48 in and settles within 0.02 in of the target,
pointing 90 deg, about 2 s after the press.
:::

## What you just did

The robot now has two drivers, and they never argue, because one line settles it. A stick past 0.1
wins. The wheels the sticks commanded stay commanded, and commanded wheels beat the follower, so the
only way the follower can drive at all is for the lesson to stand back and say so.

That is [task.l6](l6.md)'s door used the other way round. L6 through L13 used it to take the
wheels off the follower. This lesson uses it to give them back for a while, and it is how a real
teleop runs a scoring move: a button starts it, the driver's thumb stops it.
